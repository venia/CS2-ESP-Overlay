# CS2 ESP Overlay — журнал разработки

Статус: ⏸️ приостановлено (ждём результат следующего теста), учебный проект (C/C++ + AI), обновляется по мере тестов.
Смотри также `DOCS/Investigation.md` — более ранний отчёт по офсетам/структуре сущностей (актуален как история, но раздел "Текущее состояние" ниже — самый свежий).

## 🎯 Цель проекта

Внешний (external, без инжекта в игру) ESP-оверлей для CS2:
- прямоугольники вокруг игроков (Box ESP)
- полоски здоровья
- разделение враг/союзник по команде

## 🧩 Как устроено чтение памяти (архитектура)

1. `cs2-dumper.exe` генерирует `output/offsets.json` и `output/client_dll.json` — это **schema-офсеты** (поля классов, которые движок сам публикует через reflection: `m_iHealth`, `m_iTeamNum`, `m_vecOrigin`, `m_pGameSceneNode` и т.д.) и несколько глобальных указателей (`dwEntityList`, `dwLocalPlayerPawn`, `dwViewMatrix`, `dwGameEntitySystem`).
2. `cs_main.cpp` при старте запускает `cs2-dumper.exe`, парсит JSON (`LoadOffsetsFromDumper`) и получает актуальные офсеты без ручного вбивания констант.
3. Локальный игрок читается напрямую: `clientBase + dwLocalPlayerPawn` → указатель на пешку → `+0x330` (`m_pGameSceneNode`) → `+0x80` (`m_vecOrigin`).
4. Остальные сущности (боты/враги) читаются через `dwGameEntitySystem` — самый проблемный участок, см. ниже.
5. Отрисовка — GDI, прозрачное окно поверх игры (`WS_EX_LAYERED | WS_EX_TRANSPARENT`), `WorldToScreen` через `dwViewMatrix` (4×4 матрица).

## 🔍 Сессия 2026-09-06 — найдена и исправлена главная ошибка

### Диагноз

Все schema-офсеты (`m_iHealth=0x34C`, `m_iTeamNum=0x3E7`, `m_lifeState=0x354`, `m_pGameSceneNode=0x330`, `m_vecOrigin=0x80`) — **правильные**, сверены с дампом `output/client_dll.hpp`. Проблема была не в них.

Настоящий баг — в обходе `CGameEntitySystem` (`cs_main.cpp`, функция `GetPlayers`). Старый код:

```cpp
// БЫЛО (неверно):
uintptr_t listEntry = 0;
ReadMemory(hProcess, entitySystem + 0x10 + i * 0x8, listEntry);
uintptr_t entity = 0;
ReadMemory(hProcess, listEntry + 0x0, entity);
```

`entitySystem + 0x10` (`m_EntityPtrArray`) — это не плоский массив сущностей, а массив указателей на **чанки по 512 сущностей**. Внутри чанка сущности лежат структурами `CEntityIdentity` размером `0x78` (120) байт, а указатель на саму сущность (`m_pInstance`) — первое поле такой структуры (смещение `0x0`).

Старый код для каждого `i` читал не следующую сущность внутри чанка, а **следующий указатель на чанк** (шаг `0x8` вместо `0x78`), из-за чего дальше первого-двух индексов начинался мусор — отсюда "Health passed: 0, Team passed: 0" из Investigation.md.

### Исправление

Добавлена функция `GetEntityByIndex` с правильной двухуровневой арифметикой:

```cpp
constexpr int ENTITIES_PER_CHUNK = 512;      // 0x200
constexpr int ENTITY_IDENTITY_SIZE = 0x78;   // 120 байт

uintptr_t GetEntityByIndex(HANDLE hProcess, uintptr_t entitySystem, int index) {
    int chunkIndex = index / ENTITIES_PER_CHUNK;   // index >> 9
    int entryIndex = index % ENTITIES_PER_CHUNK;   // index & 0x1FF

    uintptr_t chunkPtr = 0;
    if (!ReadMemory(hProcess, entitySystem + 0x10 + chunkIndex * 0x8, chunkPtr) || !IsValidAddress(chunkPtr))
        return 0;

    uintptr_t entity = 0;
    ReadMemory(hProcess, chunkPtr + entryIndex * ENTITY_IDENTITY_SIZE, entity);
    return entity;
}
```

`GetPlayers` теперь вызывает `GetEntityByIndex(hProcess, entitySystem, i)` вместо ручного расчёта.

**Формула подтверждена независимым источником** — публичный репозиторий `aci1337/CS2-External` (`Entity.cpp`) использует буквально ту же арифметику:
```cpp
ReadMemory<DWORD64>(EntityPawnListEntry + 0x10 + 8 * ((Pawn & 0x7FFF) >> 9), EntityPawnListEntry);
ReadMemory<DWORD64>(EntityPawnListEntry + 0x78 * (Pawn & 0x1FF), EntityPawnAddress);
```

### Дебаг-инструментарий, добавленный в `GetPlayers`

Раз в ~60 кадров (`isDebugFrame`) выводится:
```
[DEBUG] entitySystem=0x... highestIndex=... rawValidEntities=... passedPlayerCheck=... totalPlayers=...
```
и для каждой найденной "сырой" сущности (сейчас лимит поднят до 60, чтобы видеть все):
```
[DEBUG]   idx=N entity=0x... vtable=0x... (vtable-clientBase=0x...) health=... team=... lifeState=...
```
`vtable` — первые 8 байт по адресу сущности; если это указатель внутрь `client.dll` (маленькая разница `vtable-clientBase`), сущность настоящая. Если `vtable` — большое число/невыровненный адрес, это мусор (пустой/освобождённый слот), и такие сущности должны отсеиваться `IsPlayerEntity`.

### Тест №1 после фикса (лимит вывода = 6)

`entitySystem` и `highestIndex=175` читаются корректно. `rawValidEntities=41` из 175 индексов — уже осмысленное число (правдоподобно для матча с ботами: игроки + оружие + пропы). `idx=0` — это `world`-сущность, читается идеально (`vtable` внутри `client.dll`, health=0/team=0 — так и должно быть у world). Но `passedPlayerCheck=0`.

Причина оказалась в самом дебаг-выводе: он был искусственно ограничен первыми **6** сущностями по индексу (0,1,4,10,11,24 — не игроки, а world/пропы), хотя всего валидных было 41. Лимит подняли до 60, чтобы видеть все.

### Тест №2 после фикса (лимит вывода = 60, полный список из 41-43 сущностей)

Пользователь подтвердил: матч с ботами реально шёл, боты двигались на экране. Прогнали полный лог всех сущностей. Разбор:

- Только **4 сущности из 41-43** имеют по-настоящему валидный `vtable` внутри `client.dll` (маленькая разница `vtable-clientBase`, не underflow): `idx=0` (world, health=0/team=0 — верно), `idx=84`, `idx=126`, `idx=168`.
- У `idx=84` и `idx=126` — `team=2` (похоже на команду), но `health=0` и `m_lifeState` (смещение `0x354`) **ненулевой и растёт от кадра к кадру** (256→257→258…). Это не похоже на живого игрока: скорее всего это не пешка игрока, а какая-то другая сущность командного/игрового уровня (правила раунда, триггеры и т.п.), у которой поле `m_iTeamNum` тоже существует (оно есть у любой `C_BaseEntity`), а по смещению `0x354` в её конкретном классе лежит не `m_lifeState`, а что-то другое (счётчик/таймер) — то есть **не факт, что оффсет `m_lifeState` универсален для всех подклассов одинаково в рамках этой проверки**, либо это действительно не игрок.
- Остальные ~37-39 "сырых" сущностей — мусор: адреса не выровнены (например, `0x22068f1bc3a` — не кратно даже 8), либо `vtable` явно не в `client.dll` (гигантские числа из-за underflow при вычитании `clientBase`). Значения при этом **стабильны из кадра в кадр** (одни и те же адреса/мусорные "поля" на протяжении многих секунд) — похоже на неактивные/освобождённые слоты `CEntityIdentity`, чья память переиспользована под служебные данные (например, указатель на следующий свободный слот в freelist), а не на реальные объекты.
- **Ни одной сущности с одновременно `team∈{2,3}` и `health` в диапазоне 1-100 и `lifeState==0` не найдено.** То есть либо живые пешки ботов физически не входят в диапазон индексов `0..highestIndex`, который мы перебираем, либо (менее вероятно) что-то не так с самим `entitySystem`/`dwGameEntitySystem`.
- Дополнительно замечено: `highestIndex` **уменьшается** со временем между снимками (175→173→172→171→169) — сущности постепенно уничтожаются (типично для временных объектов: эффекты, гильзы и т.п.), это не обязательно тревожный признак сам по себе.

### Добавлена проверка "находит ли обход вообще локального игрока"

Раз мы точно знаем адрес `localPlayerPawn` (он читается отдельно и совершенно точно правильно — HP/Team/позиция локального игрока и раньше отображались верно), логично проверить: **встречается ли этот же адрес в переборе `0..highestIndex` того же `entitySystem`?**

В `GetPlayers` добавлено:
```cpp
int dbg_localFoundIdx = -1;
...
if (entity == localPlayerPawn) {
    dbg_localFoundIdx = i;   // на каком индексе нашли самого себя
    continue;
}
```
и в итоговую строку добавлены поля:
```
[DEBUG] ... localPlayerPawn=0x... localFoundAtIdx=...
```

Это ключевая диагностика на следующий шаг:
- если `localFoundAtIdx == -1` — сам обход в принципе не видит игроков (значит `entitySystem`/диапазон индексов не тот, где живут пешки игроков — нужно искать другой путь, например через `dwLocalPlayerController` → `m_hPlayerPawn` контроллеров, а не общий перебор по индексам);
- если индекс найден — значит перебор в принципе рабочий, и тогда странно, что боты не нашлись — будем разбираться отдельно с полями/классами.

## ❗ Текущий статус — сессия приостановлена, ждём новый тест

Работа приостановлена на этом месте. Код собран, но **не пересобирался и не тестировался** после добавления `localFoundAtIdx`.

Когда продолжим — план:
1. Пересобрать `cs_main.cpp`, прогнать в матче с ботами, прислать новый `[DEBUG]`-лог.
2. Посмотреть на `localFoundAtIdx`:
   - `-1` → перебор в принципе не покрывает область, где живут игроки. Следующий шаг — читать игроков через `dwLocalPlayerController` (уже есть в офсетах) и его `m_hPlayerPawn`/список контроллеров, а не через общий `CGameEntitySystem`-перебор.
   - валидный индекс → перебор рабочий, тогда разбираться, почему конкретно боты не проходят фильтр (проверить их `m_lifeState`/класс отдельно, возможно разделить обработку контроллеров и пешек).
3. Не забыть, что дебаг-код (`[DEBUG]` строки в `GetPlayers`) — временный, для финальной версии его нужно будет убрать или спрятать за флагом.
